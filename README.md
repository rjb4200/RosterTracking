# Roster Command

Fire and EMS training attendance and roster management for one department. The project is a Next.js modular monolith backed by Neon PostgreSQL.

The current implementation provides staff authentication, reference data, class lifecycle, attendance finalization/reporting, and private official roster PDF generation.

## Requirements

- Node.js 24 or later
- npm 11 or later
- A Neon PostgreSQL database for development
- Two separate PostgreSQL databases for tests when those tests are enabled: `TEST_DATABASE_URL` for integration tests and `E2E_DATABASE_URL` for the browser suite

## Local Setup

1. Install dependencies with `npm install`.
2. Create `.env` from `.env.example` and replace every placeholder.
3. Generate `AUTH_SECRET` with `npx auth secret` or another cryptographically secure generator.
4. Apply migrations with `npm run db:migrate`.
5. Seed foundation roles and permissions with `npm run db:seed`.
6. Bootstrap the first administrator as described below.
7. Start the application with `npm run dev`.

Database credentials are server-only. Never prefix them with `NEXT_PUBLIC_` or expose them to browser code.

## Official Roster PDFs

KFS-1A October 2023 is the only approved official roster PDF output; the KBEMS-E16 form is retired because the state no longer accepts it. The supplied source file and SHA-256 checksum are versioned in `src/modules/official-roster-pdfs`; mapping changes require a new approved template version and visual fixture review. Training Majors and Administrators can generate the finalized roster, while assigned instructors can generate only their own finalized classes. The same deterministic renderer supplies inline preview, browser print, download, and Resend attachments. Generated bytes are never written to object storage or database metadata. The KFS-1A lead-instructor signature and attendee initials are populated from the finalized revision; the assisting-instructor signature remains blank for physical completion. KFS-1B individual training notices are generated for Fire participants whose represented agency differs from the class host agency: the Yellow notice is appended to the Fire roster output and the White notice is emailed to the participant. FEMA output is deferred until an approved current form is supplied.

EMS (KBEMS) classes produce a completion-certificate batch: a generated student-list cover page followed by one electronically signed certificate per active participant. A participant can be sent their own certificate by email, or staff can resend one to a different address.

Official roster and certificate email delivery uses Resend with a verified `noreply@winchesterfireems.com` sender and the server-only `RESEND_API_KEY` environment variable. Every outbound email renders inside one shared Winchester Fire Department brand shell (`src/modules/notifications/layout.ts`): a department-red masthead carrying the inline logo, wordmark, and tagline, and a contact footer. The logo is embedded as an inline `cid:wfd-logo` image rather than hosted remotely. The application validates the recipient and records deliveries in a durable outbox, dispatched after finalization commits so a mail failure never blocks the class. It never retains attachment bytes in audit records. Resend and the recipient may retain the attachment under their own retention policies.

The migration, seed, and admin scripts load `.env` from the project root automatically. Next.js also reads `.env` for the running application.

## Database Workflow

Schema definitions live under `src/server/db/schema`. Generated SQL migrations live under `drizzle` and are committed for review.

```text
npm run db:generate
npm run db:migrate
npm run db:seed
```

Use `DATABASE_URL` for application runtime traffic and `DATABASE_URL_DIRECT` for migrations and administrative commands. Migrations must run once as a deployment step and never during application startup.

## Staff Accounts

Staff accounts use normalized usernames and Argon2id password hashes. Auth.js stores the login in an encrypted, secure, HTTP-only cookie for up to one year. Protected operations reload account state and permissions from Neon, so disabling an account or resetting its password invalidates existing sessions.

Administrative commands read credentials from environment variables so passwords do not appear in command history.

### Bootstrap Administrator

Set `ADMIN_USERNAME`, `ADMIN_PASSWORD`, and optionally `ADMIN_DISPLAY_NAME`, then run:

```text
npm run admin -- bootstrap
```

Run `npm run db:seed` first. Bootstrap is idempotent and grants the administrator role.

### Create Staff Accounts

Create an instructor or Training Major account the same way. Roles are `administrator`, `instructor`, and `training-major`.

```text
ADMIN_USERNAME=jsmith ADMIN_PASSWORD=... ADMIN_DISPLAY_NAME="Jane Smith" npm run admin -- create instructor
ADMIN_USERNAME=tmajor ADMIN_PASSWORD=... npm run admin -- create training-major
```

All staff roles currently land on the same protected staff area; role-specific tools (class creation, reporting queues) are added in later phases.

### Account Operations

Set `ADMIN_USERNAME`; password reset also requires `ADMIN_PASSWORD`.

```text
npm run admin -- reset-password
npm run admin -- unlock
npm run admin -- disable
npm run admin -- enable
```

These operations are audited. Passwords and password hashes are excluded from audit details.

## Verification

```text
npm run check        # lint + static types (fast inner loop)
npm run verify       # check + unit + integration + build
npm run verify:full  # verify + smoke + browser suite
npm run smoke        # read-only critical pages
```

Unit tests do not require production credentials. The integration and browser suites each use their own database and are reset from committed migrations and seeds before a run; `verify` and `verify:full` do this for you. Run `npm run db:reset:integration` or `npm run db:reset:e2e` to prepare a database by hand.

Integration tests skip clearly when `TEST_DATABASE_URL` is absent, and the browser suite skips when `E2E_DATABASE_URL` is absent. Authenticated browser scenarios also require `E2E_STAFF_USERNAME` and `E2E_STAFF_PASSWORD` for a staff account bootstrapped in the end-to-end database.

Install the Playwright Chromium browser once with `npx playwright install chromium`.

See `docs/verification.md` for the tiers, the reset behavior, and the production guard.

## Deployment

- Deploy the application to Vercel using the Node.js runtime and Fluid Compute.
- Place Neon and Vercel compute in the same region.
- Set these in the Vercel project dashboard:
  - `DATABASE_URL` — Neon connection string for the running application.
  - `AUTH_SECRET` — cookie encryption secret for staff login.
  - `CREDENTIAL_ENCRYPTION_KEY` — **required**; encrypts stored FFN/KEMSIS credentials, staged sign-in state, and class access PINs. It must match the key the data was written with. Back it up: losing it makes stored credentials and PINs unreadable, and no code change can recover them.
  - `NEXTAUTH_URL` — optional; set to the production URL if NextAuth logs origin warnings.
  - `RESEND_API_KEY` — server-only Resend key after verifying `noreply@winchesterfireems.com`.
- Do **not** add `DATABASE_URL_DIRECT`, `TEST_DATABASE_URL`, or the `ADMIN_*` variables to Vercel; those are local/CI only.
- Apply migrations (`npm run db:migrate`), seed (`npm run db:seed`), and bootstrap the administrator against the Neon database from a trusted machine before staff can log in.
- Apply reviewed migrations through CI or an explicit release step before deploying schema-dependent code.
- Keep the runtime pool small and monitor aggregate Neon connections.
- Do not run migrations automatically from a Vercel Function.

### Credential key health

`CREDENTIAL_ENCRYPTION_KEY` is the single most dangerous value to get wrong. If it is missing, malformed, or replaced with a different key, class access PINs and stored credentials silently stop decrypting, and students see "sign-in unavailable" with no explanation.

Check it at any time as an authenticated staff member:

```text
GET /api/staff/key-health
200 { "healthy": true,  "probeOk": true,  "openClassPinOk": true,  "message": "Credential key is healthy." }
503 { "healthy": false, "probeOk": true,  "openClassPinOk": false, "message": "Stored credentials and PINs cannot be read. Verify CREDENTIAL_ENCRYPTION_KEY matches the key used when the data was written." }
```

`probeOk` false means the key itself is unusable (missing or not 32 base64-encoded bytes). `openClassPinOk` false while `probeOk` is true means the key works but does not match the key that wrote the stored data — the classic rotated-key fault.

**Operator response when key health fails:**

1. A `probeOk: false` result is a deployment fault. Restore the correct `CREDENTIAL_ENCRYPTION_KEY` value from the backup and redeploy.
2. An `openClassPinOk: false` result means the running key differs from the historical key. **Do not** simply accept it: stored credentials and finalized attendance snapshots encrypted with the old key remain unreadable.
3. Recovering rotated-key data requires the original key. Per `ARCHITECTURE.md`, rotating the credential key needs a planned, versioned migration that re-encrypts existing values while the old key is still available. Replacing the environment value alone is not a rotation.
4. Until it is resolved, read-only probes and the startup warning will keep reporting the fault, and PIN-gated classes cannot be entered. Classes without a PIN still work, but credential recovery and official roster PDFs that read encrypted snapshots will not.

Production launch also requires Neon point-in-time recovery, scheduled snapshots, separate logical exports, backup alerts, and a tested restoration procedure. See `ARCHITECTURE.md` and `ROADMAP.md` for durable design decisions and phased work.
