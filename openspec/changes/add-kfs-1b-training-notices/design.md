## Context

See `proposal.md` — Why. Current state that shapes the approach:

- The KFS-1B Light-Yellow and White files are **field-identical** (20 AcroForm fields, same coordinates), differing only in background colour.
- `official-roster-pdfs` owns versioned templates (`mappings.ts`), a `renderPage`/`renderOfficialRoster` path, and a per-form route.
- The certificate pipeline in `completion-certificates` already provides per-participant email delivery over the `notifications` outbox (post-commit dispatch, skip-if-unchanged, resend, delivery exceptions) — directly reusable.
- `roster-signing` captures the lead instructor's typed-name attestation on the revision.
- `buildSnapshot` captures each attendee's `agencyName` but **not** the class host agency; the snapshot must carry the host agency and each attendee's represented agency identity to decide eligibility from revision facts.

## Goals / Non-Goals

**Goals:**
- Produce a signed KFS-1B per outside-agency participant for a finalized Fire class.
- Email the White copy per participant at finalization; append the Yellow copies to the Fire roster output.
- Decide eligibility from the immutable revision.
- Reuse the existing delivery/outbox machinery rather than inventing a new one.

**Non-Goals:**
- No electronic (PKI) signature; the typed-name attestation matches the roster and certificate.
- No change to the certificate (EMS) path.
- No per-notice retention of generated bytes.
- Not resolving what `Agency_Selection` means (left blank for now).

## Decisions

### D1 — Two assets, one mapping, variant chosen at render time

Add `kfs-1b-light-yellow` and `kfs-1b-white` assets with their own checksums but a shared `TemplateMapping`; the renderer takes the variant as an argument.

- **Why**: the forms differ only by colour; duplicating the mapping invites drift.
- **Alternatives**: one asset and a colour overlay (fragile); separate full mappings (duplication).

### D2 — Eligibility is decided from the revision

Extend `FinalizationSnapshot` with the class host agency and each attendee's represented agency identity; qualify a participant when `attendance.agencyId ≠ class.hostAgencyId`.

- **Why**: the notice must be reproducible from the locked revision; comparing by agency name is fragile.
- **Alternatives**: compare agency names (ambiguous); read live class/attendance (breaks immutability).

### D3 — Generate on demand; never retain bytes

Render a notice from the revision on each request, like the roster and certificate.

- **Why**: consistent with the existing "reproducible, not retained" contract.
- **Alternatives**: store generated notices (new storage and retention surface).

### D4 — Sign from the attestation

Fill `Instructor_Signature` with the revision's attested typed name; blank when the revision has no attestation.

- **Why**: one signing fact across roster, certificate, and notice.

### D5 — White copy delivered through the shared outbox

At finalization, enqueue one `kfs-1b` delivery per qualifying participant and dispatch after commit, mirroring `completion-certificates` (recipient captured in the revision, skip-if-unchanged, resend, delivery exceptions).

- **Why**: identical failure isolation and UX; the delivery table is already generic.
- **Alternatives**: a new delivery mechanism (duplication).

### D6 — Yellow copy appended to the Fire roster output

The KFS-1A renderer appends the Yellow notice pages (one per qualifying participant) after the roster pages, for view, download, and email.

- **Why**: the department files one action ("view the roster") that should carry the notices.
- **Alternatives**: a separate document row (extra clicks; the user asked for appended pages).

### D7 — `Agency_Selection` is left blank

The field is not mapped; a note records that its meaning must be confirmed against the form.

- **Why**: its label could not be read (subsetted fonts) and no safe guess exists.
- **Alternatives**: guess a value (risks a wrong state form).

### D8 — Subject rows fill from the top

Map the class's Fire subjects (`category code` + `hours`) into `Row_1..5` from the top; leave the remainder blank. A class carries at most two Fire subjects.

- **Why**: the class model already bounds Fire subjects; five rows are never all used.

## Risks / Trade-offs

- **Snapshot change** → keep host/represented agency optional so pre-existing revisions produce no notices rather than failing.
- **Agency identity by name vs id** → use ids in the snapshot to avoid ambiguity.
- **New state-form assets** → record checksums and require a visual fixture review before release, per the template governance.
- **Roster attachment grows** → a Training Major emailing the roster now also sends the Yellow notices; documented and expected.
- **`Agency_Selection` unknown** → blank today; a task re-checks it.
- **Two rendering variants** → one code path with a variant flag keeps yellow and white byte-identical except colour.

## Migration Plan

1. Add the Light-Yellow and White KFS-1B assets, mapping, and checksums.
2. Extend `buildSnapshot` (and the snapshot type) with the host agency and each attendee's represented agency identity.
3. Add the KFS-1B renderer and eligibility helpers.
4. Queue White deliveries at finalization; dispatch after commit.
5. Append the Yellow pages to the KFS-1A output.
6. Add review-screen delivery controls and resend for notices.
7. Update docs and tests.
8. **Rollback**: revert the commit; the snapshot additions are optional and no schema changes are introduced.
