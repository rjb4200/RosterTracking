# completion-certificates Specification

## Purpose
Produce the per-participant course-completion certificate that KBEMS requires as proof of completion for a continuing-education class, from the same immutable revision facts used for official rosters.
## Requirements
### Requirement: Certificates are generated from finalized revision facts
The system SHALL generate a completion certificate only from a finalized roster revision and SHALL use that revision's participant, class, instructor, and course facts rather than mutable current records.

#### Scenario: Generate a certificate
- **WHEN** authorized staff generate a certificate for a finalized revision
- **THEN** the certificate contains the participant, class, instructor, and course facts preserved by that revision

#### Scenario: Block a non-finalized source
- **WHEN** staff attempt to generate a certificate for a class without a finalized revision
- **THEN** the system rejects the request without returning a certificate

### Requirement: One certificate per participant
The system SHALL produce a separate certificate for each active participant of the finalized revision, addressed to that participant.

#### Scenario: Generate for every participant
- **WHEN** a finalized revision has several active participants and staff request certificates
- **THEN** the system produces one certificate per participant with that participant's name

#### Scenario: Exclude removed attendance
- **WHEN** a participant's attendance was removed before finalization
- **THEN** no certificate is produced for that participant

### Requirement: Certificate content
Each certificate SHALL show the participant name, the class hours, the course type, the course number, the course-completion date, and the instructor name, and SHALL render the instructor title and the class name on the signature line. The certificate SHALL render the lead instructor's typed-name electronic signature derived from the finalization revision's attestation, and SHALL leave the signature blank only when the revision has no recorded attestation. The certificate SHALL leave the instructor signature blank for physical signing only in that no-attestation case.

#### Scenario: Populate certificate fields
- **WHEN** a certificate is generated
- **THEN** the participant name, class hours, course type, course number, completion date, and instructor name are populated

#### Scenario: Omit a missing optional value
- **WHEN** the class has no course number
- **THEN** the certificate leaves that field blank rather than printing a placeholder

#### Scenario: Render the electronic signature
- **WHEN** a certificate is generated from a revision with a recorded attestation
- **THEN** the instructor signature area shows the attested signer's typed name

#### Scenario: Leave the signature blank without an attestation
- **WHEN** a certificate is generated from a revision with no recorded attestation
- **THEN** the instructor signature area is left blank

### Requirement: Certificate generation is controlled and audited
The system SHALL allow an assigned instructor to generate certificates only for a finalized class to which they are assigned, and Training Majors and Administrators to generate them for any finalized class. The system SHALL record the actor, the revision, the participant, and whether the certificate was electronically signed, and SHALL not retain generated certificate bytes.

#### Scenario: Permit an assigned instructor
- **WHEN** an instructor generates certificates for a finalized class to which they are assigned
- **THEN** the system permits the request

#### Scenario: Deny an unrelated instructor
- **WHEN** an instructor generates certificates for a finalized class to which they are not assigned
- **THEN** the system denies access without disclosing certificate content

#### Scenario: Record the signature source
- **WHEN** a certificate is generated
- **THEN** the system records an audit event noting the actor, the participant, and whether the signature was rendered from the revision's attestation

#### Scenario: Do not retain generated bytes
- **WHEN** the same certificate is requested again
- **THEN** the system regenerates it from the revision without retaining the earlier copy

### Requirement: The admin batch pairs a student list with certificates
The system SHALL produce, for a finalized EMS class, one PDF that begins with a student-list cover page listing the class and each active participant's name, represented agency, and credited hours, followed by one certificate page per active participant. The cover page SHALL be generated by the system and SHALL NOT reproduce a retired state form.

#### Scenario: Produce the batch
- **WHEN** authorized staff request the certificate batch for a finalized EMS class
- **THEN** the system returns one PDF whose first page lists the participants and whose remaining pages are one certificate per active participant

#### Scenario: List every active participant
- **WHEN** a finalized revision has several active participants
- **THEN** the cover lists each active participant and the PDF contains a certificate for each

#### Scenario: Exclude a removed participant
- **WHEN** a participant's attendance was removed before finalization
- **THEN** the cover and certificates omit that participant

### Requirement: Certificates are delivered to each participant at finalization
When an EMS class is finalized, the system SHALL send each active participant their own certificate as a PDF attachment from `noreply@winchesterfireems.com` to the email captured in the finalization revision, and SHALL record each delivery. Delivery SHALL NOT block or roll back finalization.

#### Scenario: Email each participant
- **WHEN** a finalized EMS revision has several active participants
- **THEN** the system sends each participant their own certificate to that participant's captured email

#### Scenario: Do not email a removed participant
- **WHEN** a participant's attendance was removed before finalization
- **THEN** no certificate email is sent to that participant

#### Scenario: Do not email a non-EMS class
- **WHEN** a finalized class did not report to KBEMS
- **THEN** the system does not send certificate emails

#### Scenario: Finalization survives a delivery failure
- **WHEN** a certificate email cannot be delivered
- **THEN** the finalization still succeeds and the failed delivery is recorded

### Requirement: Unchanged certificates are not re-sent
The system SHALL NOT send a participant a certificate email when the certificate that would be produced is unchanged from the participant's last successfully delivered certificate, ignoring the template version. The system SHALL send again when any certificate value changes.

#### Scenario: Suppress an unchanged resend
- **WHEN** a finalized class is reopened and finalized again and a participant's certificate values are unchanged
- **THEN** the system does not send that participant another certificate email

#### Scenario: Send after a change
- **WHEN** a class name, credited hours, course type, course number, completion date, instructor name, or participant name changes and the class is finalized again
- **THEN** the system sends the affected participant a new certificate email

### Requirement: Staff can resend a participant's certificate
The system SHALL let authorized staff resend an individual participant's certificate, optionally to an operator-supplied email address, without changing the stored participant profile. The system SHALL record the actor and the recipient for each resend.

#### Scenario: Resend to the captured address
- **WHEN** authorized staff resend a participant's certificate without entering a different address
- **THEN** the system sends it to the email captured in the finalization revision

#### Scenario: Resend to a different address
- **WHEN** authorized staff resend a participant's certificate and supply a different address
- **THEN** the system sends it to that address without altering the stored participant email

### Requirement: Undeliverable participants are surfaced
The system SHALL identify finalized active participants without a deliverable email address and present them as delivery exceptions on the review screen, with an action to provide an address and send. An undeliverable participant SHALL NOT block finalization.

#### Scenario: List a participant missing an email
- **WHEN** a finalized revision has an active participant with no email
- **THEN** the review screen lists that participant as a delivery exception

#### Scenario: Send after providing an address
- **WHEN** authorized staff supply an address for a delivery exception
- **THEN** the system sends that participant's certificate to the supplied address

#### Scenario: Still finalize
- **WHEN** a participant has no deliverable email
- **THEN** the class still finalizes
