description: "Promote verified RosterTracking code to production with backups, migrations, verification, and issue closure"

Deploy the requested verified development release to production. Arguments: `$ARGUMENTS` (optional OpenSpec change, PR, issue, or exact release SHA). This workflow may affect live staff data: production-changing actions require explicit approval of the release plan and migration/rollback plan.

## Non-negotiable release gates
- Follow `docs/environment-workflow.md`, `docs/operations.md`, and OpenSpec artifacts; use a named OpenSpec change when supplied, otherwise identify relevant changes/PRs/issues from git history. Never assume every issue on a branch shipped.
- First show a release plan: source and target refs, exact commit SHA, deployment environment and URL, database identity (redact connection strings), migration list, associated GitHub PRs/issues, risk, verification, and rollback.
- Use existing workflows and supported Vercel/Neon/GitHub tools. Verify actual workflow configuration and deployment state; do not pretend an agent command is a CI gate. Never guess a deployment ID, app URL, or database target.
- Ensure clean working tree for any local release actions, synced remote branches, no secrets committed, no direct commits to `main`, required CI green, passing `npm run check:migrations -- set`, and committed generated migrations. Run/check `npm run verify` with test DB configured; an integration test skipped due to absent credentials is NOT a pass. Add `verify:full` when browser-critical changes justify it, with test DBs isolated from dev/prod.
- Compare migration ledger with committed SQL using `npm run db:status` (production requires `-- --allow-production`). Treat skipped, edited, or uncommitted-applied migrations as blockers, not as issues to auto-fix. A pre-migration nonzero exit with *only pending* migrations is expected; explicitly examine output rather than accepting any failure. After applying, status MUST exit zero and say `In sync.`
- Use `DATABASE_URL_DIRECT` only for migrations; verify target database and Neon branch separately from `DATABASE_URL` and Vercel environment scope. Never print credential values. No destructive reset/provision/import/seed unless separately required, reviewed, and explicitly authorized. No migration during application startup.
- Coordinate schema and app rollout: use backward-compatible expand/migrate/contract changes for breaking schemas. Stop if the existing running version would break after migration; propose staged release instead.
- Verify actual deployed SHA, runtime logs, representative authenticated and public workflows, correct environment URL, key-health endpoint (authenticated staff access), and data integrations applicable to the change. Do not expose secrets or real attendee data in logs.
- On any failed gate, stop and report precise failure and safe recovery. Never claim success from a mere push or Vercel build.
- GitHub issue closure: identify linked issues from OpenSpec proposal/tasks, PR body, and explicit issue references; do not infer from keyword matches alone. Record deployment evidence and the deployed SHA/URL on the issue/PR. Close only issues whose acceptance criteria are verified in the intended environment. Keep others open; never auto-close unrelated issues.
- OpenSpec: validate applicable changes, check task completion, and sync/archive only according to existing `/opsx-sync` and `/opsx-archive` guidance; never archive partially deployed changes.

## Production procedure
1. Inventory exactly what is being promoted from `dev` to `main`, including ALL commits and migrations in the promotion PR, and map accepted OpenSpec changes and issue numbers. Require verified dev release of same candidate code, no unexpected branch divergence, green PR checks (including append-only migrations), required review, and no direct push to `main`.
2. Verify production backup health, recent restore drill, point-in-time recovery, and snapshot/restore option. Take and verify a pre-release Neon snapshot with an identifiable label before schema/data writes. A restore drill must use `finalize: false` on a separate branch; never replace production as a routine rollback.
3. Inspect the production connection using a trusted runner with explicitly scoped `DATABASE_URL_DIRECT` and `PROTECTED_DATABASE_NAMES`. Compare runtime and direct database identity without exposing credentials; do not use local dev `.env` by accident. Run `npm run db:status -- --allow-production`, inspect all states; STOP on edited/skipped/uncommitted-applied migrations.
4. Coordinate the release with Vercel: **main merges may automatically deploy production**. Do not merge until a migration-compatible release sequence is established. For compatible additive migrations, apply reviewed migrations through a protected trusted job with `npm run db:migrate -- --allow-production`, verify `npm run db:status -- --allow-production` returns `In sync.`, then approve/merge the `dev -> main` PR and verify the exact build goes live. If branch protection or auto-deploy prevents safe sequencing, STOP and propose a controlled GitHub Actions/Vercel release gate first; do not race an auto-deploy. Breaking migrations require a multi-release expand/contract plan.
5. Verify production app SHA, correct production Neon database and domains, authentication/authorization, public sign-in, attendance/class lifecycle as applicable, official roster/PDF generation, email outbox delivery monitoring without real test emails, staff credential encryption key health, migration ledger, and Vercel runtime logs. Prefer non-destructive checks with test accounts/data. Verify monitoring/alerts and no unexpected errors; compare critical row counts if data changes.
6. Publish release notes and a GitHub deployment record/status if available. Link PR, OpenSpec change, commit SHA, migration identifiers, snapshot reference (non-secret), Vercel deployment ID/URL, and validation results. Comment on associated GitHub issues and close **only** issues meeting their acceptance criteria in production; preserve unresolved issues with clear follow-up. Sync/archive completed OpenSpec work according to OpenSpec commands, not merely because code merged.
7. On failure: STOP further promotion/issue closure, capture impact, consider Vercel code rollback **only if schema remains compatible**, and escalate database recovery to a separately approved Neon restore procedure. Never automatically reverse forward-only migrations or overwrite production data.

## Final report
State status: PASS, BLOCKED, or PARTIAL; explicit approval and release reference; deployment URL and SHA; snapshot/backup evidence; migration before/after; production validation; issues closed vs left open (with reasons); rollback path and follow-up.
